# Russia–NATO Monitor — анализ существующих проектов и план MVP

Дата: 2026-10-02.

## 0. Что оказалось «AI News проектом»

На компьютере два связанных проекта:

| Проект | Стек | Что в нём ценного | Статус |
|---|---|---|---|
| `Documents/AI_monitoring` («AI Newsroom») | TypeScript, Next.js 16, Prisma, PostgreSQL/Neon, Gemini | конвейер collect → normalize → relevance → embed → cluster → analyze; Gemini free tier; эмбеддинги + косинус (ADR-005); бюджет-капы; GitHub Actions cron | развёрнут (Neon + Actions), **Telegram нет** |
| `Codex/2026-09-27/.../telegram-ai-news` | Python 3.12, SQLAlchemy, FastAPI | Telegram-очередь с честной обработкой неоднозначной доставки (`sending` → `uncertain`), `event_key` от LLM для дедупа, русская редактура, дневной лимит LLM-вызовов в БД | не развёрнут, LLM не настроен; **Python на машине не установлен** |

## 1. Что переиспользуем

- **Форма конвейера** AI Newsroom (collect → дёшевые фильтры → LLM-скрининг → эмбеддинги → кластеризация → анализ) — один-в-один по идее.
- **Gemini free tier** — уже проверенный бесплатный провайдер, ключ есть. `gemini-flash-lite-latest` (самая щедрая квота), эмбеддинги `gemini-embedding-001` (768 dims, нормализация), косинус в приложении без pgvector (ADR-005). Фолбэк: другие flash-модели и Gemma 4 (отдельная квота).
- **Кластеризация**: косинус к центроиду события + подтверждающие эвристики + `event_key` от LLM (идея из telegram-ai-news). Консервативные пороги: лучше два события, чем ложное слияние.
- **Telegram-доставка** из telegram-ai-news: очередь в БД, `sending` фиксируется до запроса, неоднозначный ответ → `uncertain` и без слепого повтора, 429 → `retry_after`.
- **Run-капы**: лимит LLM-вызовов на запуск и в сутки, учитываемый в БД.
- **Деплой-модель**: GitHub Actions cron вместо постоянного сервера.

## 2. Что меняем

- **Стек**: Node 24 + TypeScript без сборки (нативный type stripping) + встроенный `node:sqlite`. Без Next.js/Prisma: каналу не нужен веб-сервер, а Python нет на машине. Минимум зависимостей.
- **База**: SQLite-файл, который Actions хранит в отдельной ветке `state` (orphan-коммит, force-push → репозиторий не растёт). Ноль новых аккаунтов (не нужен Neon/Supabase). Старые тексты статей регулярно обрезаются.
- **Relevance**: вместо одного LLM-вызова на статью — **пакетный триаж** (≈25 заголовков+лидов за вызов) после многоязычного ключевого префильтра. Это то, что делает бесплатную квоту достаточной при 100+ источниках.
- **Анализ события** — не «AI-брифинг», а редакционная модель: FACT / OFFICIAL_CLAIM / OSINT_CLAIM / ASSESSMENT / ANALYSIS / UNCONFIRMED, направление сигнала (эскалация / контрсигнал / нейтрально), новизна относительно уже опубликованного, даты события vs публикации.

## 3. Что добавляем (в AI-проектах этого нет)

1. Реестр источников в БД с tier'ами (A official/intel, B agency, C quality media, D local, E think tank, F OSINT, G social), стороной (NATO / RU / BY / нейтральная) и надёжностью.
2. Коллекторы: RSS/Atom, **публичные Telegram-каналы через `t.me/s/`** (без API-ключей), **GDELT DOC API** (бесплатный многоязычный discovery), Bluesky public API, автопоиск RSS на странице.
3. Цепочка источников и **независимость подтверждений** (перепечатки одного Reuters ≠ 10 подтверждений).
4. Новизна: NEW / SIGNIFICANT_UPDATE / MINOR_UPDATE / DUPLICATE / BACKGROUND / OLD_RESURFACED.
5. Importance 0–100 (объяснимые компоненты) и отдельный **Escalation Signal Index** 0–100 с историей и драйверами/контрсигналами. Явно не вероятность войны.
6. Source discovery: ссылки и упомянутые организации из релевантных статей → `source_candidates`, автопоиск фида, автопродвижение в `testing`, рейтинг по фактической полезности (кто первый, кто подтвердился).
7. Source health: мёртвые/молчащие источники, авто-поиск нового URL фида.
8. Редакционный контроль через **Telegram-бота в личном админ-чате** (preview, approve/reject кнопками, команды `/pending`, `/sources`, `/candidates`, `/why N`) — опрос `getUpdates` каждым циклом, сервер не нужен. Плюс статический HTML-отчёт (`npm run report`).
9. Ежедневная сводка в формате «Россия—НАТО | Сводка за …».
10. Защита: запрет точных координат, запрет сгенерированных ссылок, CLAIM не может стать FACT при рерайте (валидация).

## 4. Что из AI-архитектуры здесь не подходит

- Веб-фид Next.js как основной продукт — продукт здесь Telegram.
- «Слухи разрешены с пометкой» (AI-канал) → здесь неподтверждённое из соцсетей вообще не публикуется как новость без попытки подтверждения; максимум «утверждение X» с атрибуцией.
- Социальные сигналы HN/points как фактор важности — нерелевантно; популярность ≠ надёжность.
- Недельный дайджест/YouTube-ветка — заменяется ежедневной сводкой и индексом.
- Отбрасывание неанглоязычных статей (`INGEST_KEEP_LANGUAGES=eng`) — здесь многоязычие обязательно.

## 5. Бесплатные ограничения (честно)

| Компонент | Ограничение | Как обходим |
|---|---|---|
| Gemini free tier | лимиты RPM/RPD на модель, могут меняться | пакетный триаж, капы на запуск/сутки, цепочка фолбэк-моделей, Gemma 4. Рекомендуется **отдельный ключ** (отдельный Google Cloud project), чтобы не делить квоту с AI Newsroom |
| GitHub Actions | приватный репо — 2000 мин/мес | цикл раз в 2 ч (~5 мин) ≈ 1800 мин. Публичный репо → безлимит и можно раз в час |
| Reuters / AP / AFP | нет публичных RSS | через GDELT-поиск и цитирование в других СМИ; оригинал ищем по ссылкам |
| X (Twitter) | бесплатного API для чтения нет | не подключаем; Telegram `t.me/s/` + Bluesky + RSS исследователей |
| kremlin.ru / mil.ru | часто гео-блок для зарубежных IP | Telegram-каналы ведомств как зеркало (`mod_russia`, `MID_Russia`) |
| Разведслужбы | почти нет RSS, публикуют редко (годовые отчёты) | ловим через новости + GDELT; домены разведслужб имеют tier A для атрибуции |
| GDELT | ~1 запрос / 5 с, иногда нестабилен | несколько запросов за цикл с паузами; сбой не ломает цикл |

## 6. Минимальный путь к MVP

1. Каркас: config, SQLite-схема, логгер, http-клиент с лимитами.
2. Seed-реестр источников + скрипт живой проверки фидов → оставляем только рабочие.
3. Коллекторы RSS / Telegram / GDELT → `articles` (дедуп по URL и заголовку, даты).
4. Ключевой префильтр + пакетный LLM-триаж (релевантность, категория, тип утверждения, сторона, дата события, оригинальный источник, упомянутые организации/ссылки).
5. Эмбеддинги + кластеризация в события; цепочка источников, независимые подтверждения.
6. Анализ события → русский пост + классификация + importance + новизна.
7. Очередь публикаций (dry-run по умолчанию), админ-бот, отчёт.
8. Индекс эскалации + ежедневная сводка.
9. Discovery + health.
10. GitHub Actions (cron) + ветка `state`.

Каждый шаг проверяется на реальных источниках.
